ACTION — one thing to know, stated carefully because I got it wrong in both directions before settling. Every one of your 44 database tables grants TRUNCATE to both the logged-in role AND the anonymous role, and row-level security does not apply to TRUNCATE at all — no policy restricts it and none can. I originally told sysadmin this was "no live exposure"; that was wrong. But I am not overstating it either: the API layer doesn't offer a TRUNCATE operation, so there is no known way to trigger it from a browser today. The honest position is that your database's protection against a signed-in user destroying every table is currently that the HTTP layer happens not to offer the verb — which is not a control. The fix is one line and it is in the migration now. Nothing is known to be exploitable. The full migration DDL is drafted and with sysadmin to countersign and apply; that is gate 1 on the High Line proposal.

01Scope of this document

A technical description of what AuthorsLab does, how it is built, where data goes, and what it does not yet have. Written for a reader whose job is to find the problems.

  • Where something is not built, this document says so.
  • Where something is unresolved, it says that too, and gives the date we expect to resolve it.
  • Figures quoted are measured on real manuscripts, not modelled. Where a figure is extrapolated it is labelled.
A specification that contains only good news is a brochure. We would rather hand you something you can argue with.

02What AuthorsLab is

A working environment for a publishing house's editorial department. A house ingests the titles on its list; its editors work on them inside the system; the system produces editorial analysis that a named human reviews, approves and sends on.

  • The house owns the copy. Every title is house-ingested. Authors are not users of the system.
  • Editorial output leaves as a document — a package sent by a named person at the house. There is no author-facing portal and no cross-party messaging.
  • Human judgement stays with your team. The system holds no opinion an editor has not approved.

03What the system does

Intake

  • Accepted formats: Microsoft Word (.docx) and PDF.
  • Text extraction, validation and chapter segmentation on ingest. Front matter, prologues and epilogues are detected and stored under the author's own labels rather than renumbered.
  • Ingest is gated. A file that fails validation is refused with a stated reason, not loaded in a degraded state (see §5).

Full manuscript read

  • Five analyses run in parallel against the complete manuscript — structural, character, plot, pacing, thematic — followed by a single synthesis pass across all five. Six model calls per read, each separately recorded.
  • Per-chapter analysis and a chapter summary set are produced alongside.
  • Editorial dialogue: an editor can interrogate the analysis in conversation, scoped to that manuscript.

Outputs

  • Full editorial report — typeset PDF, house-branded.
  • Chapter summaries — one per chapter.
  • Key points — the compressed form, designed to be carried forward.

  • Turnaround is close to flat with manuscript length. A 36% larger book took 4% longer, because the five analyses run concurrently against the whole text — wall-clock time is dominated by model latency, not word count.
  • Quoted range: 30–40 minutes for a 30,000–90,000 word manuscript. Outside that range the figures are extrapolated and labelled as such in the interface.
  • A read does not depend on anyone's browser. The job record exists server-side; the editor is notified on completion.

04The method: a language model is an unreliable industrial component

This is the part we believe is unusual, and the reason a house can put unpublished manuscripts through it. Most tools call a model and display the answer. We treat a model call the way a factory treats a machine on a line.

Four properties, all live today

  • Every model call is a job with a record. Registered before it starts, carries a timeout, ends in an explicit terminal state — ready, failed or timed out. A run that never finishes is detected and recorded rather than quietly disappearing.
  • One door to the model. All model access passes through a single component that records model, token counts and cost per call. There is no second path and no ad-hoc call anywhere in the system.
  • Every output is checked by something that did not produce it. An independent layer re-derives what the output should contain from the source material and compares. It never asks the component that did the work whether the work was done. Each check cites the rule it enforces and ships with a control that makes it fail on demand.
  • When we cannot do something properly, we refuse. No approximation, and no degraded result presented as a complete one. Where a feature is unfinished the interface says so rather than offering a control that appears to work.
A check nobody has watched fail is not known to work. Nothing on screen may claim more than its evidence supports.
  • A completed stage shows who completed it, and whether that was a person or the system.
  • An absent value is shown as absent — never as a plausible default.
  • Editorial decisions are recorded with a server-derived actor and timestamp, and are not editable afterwards.

05Evidence, from your own manuscript

We would rather demonstrate §4 than assert it. Both examples below are from The List, ingested this week.

It found an error we did not put there

  • On ingest the system reported that chapters 19, 47 and 78 are labelled 20, 48 and 76 in the source file.
  • All 82 chapters loaded. The discrepancy was flagged, with the specific chapters named. No content was lost and nothing was silently corrected.

It refused a file

  • An earlier PDF of the same manuscript decoded its fonts incorrectly — every fi and fl ligature rendered as a digit, affecting 646 words across 361,000 characters.
  • The text was perfectly legible and completely wrong. Rather than analyse it, the system detects that signature and rejects the file, naming the Word document as the alternative.
A corrupted manuscript that looks fine is worse than a rejected one.

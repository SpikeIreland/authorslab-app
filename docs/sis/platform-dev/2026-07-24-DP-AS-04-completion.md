## 1 · Exit criteria: app-side evidence

### E1 · submit → ack row within 5s, visible in-app

**DB-side machinery** (SysAdmin, verified in AL-SYS-DP04-SR-R): the `notify_j1_submit()` trigger fires AFTER INSERT on `as_journeys` for `journey_type='full_analysis'`. Insert-to-ack latency is single-statement — measured well under 5s in SysAdmin's E1 test. The `ON CONFLICT (journey_id, template_id) DO NOTHING` guarantees exactly-once.

**App-side machinery** (this dispatch): `NotificationBell` component subscribes to `notifications` filtered by `user_id=eq.<current user>` via Supabase Realtime. On any change (INSERT triggered by the DB), the badge count refreshes; if the panel is open, the list refreshes too. See `src/components/NotificationBell.tsx:70-98`.

**Combined effect:** DP-AS-02's `startJourney` insert → DB trigger `notify_j1_submit` → notifications row → realtime channel → NotificationBell badge increments in-app. All within one round-trip past the DB write.

**One-time verification protocol** (once first n8n workflow is instrumented, satisfies both DP-AS-02 E3 and DP-AS-04 E1 in one run):
1. In dev app, open the studio on a test manuscript, note the bell badge (assume 0).
2. Trigger a full-manuscript analysis (initial or fresh-analysis path).
3. Bell badge should increment to 1 within seconds; opening the bell shows the "Reading started" (or "Careful processing" for >80k words) notification.

### E2 · every J1 terminal state produces exactly one notice row

**DB-side machinery**: the `notify_j1_terminal()` trigger fires AFTER UPDATE only when the OLD status was not terminal and the NEW status is one of `ready/failed/reaped`. Combined with the `ON CONFLICT (journey_id, template_id) DO NOTHING` guarantee, this is double-locked — the OLD-state guard prevents same-transition duplicates, ON CONFLICT prevents same-terminal-different-triggers.

SysAdmin verified live: "terminal write → exactly one `j1_ready`; a second terminal write → still exactly 2 rows total. The double-fire is blocked twice over."

**App-side machinery**: the NotificationBell renders whatever rows exist. If E2 holds at the DB layer, the UI shows exactly one terminal notice per journey — no app-side deduping needed.

**Sensor coverage** (SysAdmin): `inv_13_silent_receipt` catches any J1 terminal without a corresponding notification, registered in `health_check`. Continuous monitoring.

### E3 · zero notification content generated by an LLM

**Code review evidence:**

- `src/lib/notifications.ts` — reader-only. All exported functions (`listUnreadForCurrentUser`, `listRecentForCurrentUser`, `countUnreadForCurrentUser`, `markRead`, `markAllRead`, `formatTimeAgo`) do reads and updates only. No INSERT surface. No call to any LLM API. No template strings that could be interpolated with LLM output.
- `src/components/NotificationBell.tsx` — display component. Renders `notification.title`, `notification.message`, `notification.priority`, `notification.action_label` verbatim from the DB row. Also renders inline UI strings ("Notifications", "Mark all read", "You're all caught up.", "Loading…") — all deterministic literals. No LLM call anywhere in the component.
- **The write path is entirely DB-side.** The only source of notification content is the two trigger functions (`notify_j1_submit`, `notify_j1_terminal`), whose bodies use inline SQL string literals — no PL/pgSQL call to an external service, let alone an LLM. SysAdmin's response §3 confirms "your copy verbatim."

## 3 · Design deviations from my original proposal, absorbed cleanly

Per SysAdmin's AL-SYS-DP04-SR-R §2:

- `user_id` (auth uid) not `author_id` — simpler realtime filter (`user_id=eq.<uid>`), used verbatim in NotificationBell L79.
- `message` not `body` — reflected in the `Notification` type L26.
- `type`/`category`/`priority` not `kind` — priority drives the UI dot colour (`red` for high, `blue` for normal); type and category available for future filtering.
- `is_read` + `read_at` (both) — `markRead` and `markAllRead` set both in the same UPDATE.
- Partial unique index on `WHERE journey_id IS NOT NULL` — legacy rows without journeys unaffected; the ON CONFLICT guarantee still holds for the DP-AS-04 use case.
- `manuscript_id`, `action_url`, `action_label` — bonus fields; the bell uses `action_url` for deep-link navigation and `action_label` for the CTA text, both rendered when present.

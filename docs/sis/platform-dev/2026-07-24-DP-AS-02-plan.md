## 2 · Shared helpers I'll add

Two small functions to keep the mechanism in one place. Location: `src/lib/as_journeys.ts` (new file).

### `startJourney(supabase, args) → { journey_id, timeout_at }`

Inserts a journey row *before* the webhook fires. Returns the `journey_id` to pass in the webhook payload. All timeouts computed here from the RDP §2 spec (see §4). Args:

```ts
{
  journey_type: 'full_analysis' | 'chapter_analysis' | 'editor_chat' | 'phase_transition',
  manuscript_id: string,
  chapter_id?: string,
  editor_name?: 'alex' | 'sam' | 'jordan',
  size_hint?: { word_count?: number },   // for size-scaled full_analysis timeout
}
```

Contract: throws on insert failure (never silently returns an unusable journey_id — the caller must decide whether to skip the webhook or degrade honestly).

### `pollJourney(supabase, journey_id, opts) → { status, terminal_reason?, timed_out_at? }`

Pure read. Polls the journey row until `status` is terminal (`ready | replied | complete | rejected | failed | reaped`) or until a caller-supplied max interval passes. Never writes.

Contract: only reads. No side effects. Returns terminal state to the caller who decides what to render.

**Neither helper touches domain tables.** The old polling paths that read `manuscripts.manuscript_summary` or `manuscript_issues` count rows are replaced by `pollJourney` reading the single as_journeys row. Domain-table state remains the truth for content; journey rows are the truth for state.

## 3 · Payload changes

Every webhook body gains a `journey_id` field. The rest of the payload stays exactly as it is (backward compatible: n8n workflows that don't yet handle `journey_id` continue to run; they just don't write back status, so the row remains `submitted` until `timeout_at` and the reaper closes it — which is exactly the corpse-on-every-path behaviour we want for un-instrumented paths).

**Example — the initial full-analysis trigger, before/after:**

```ts
// before
fetch(WEBHOOKS.alexFullAnalysis, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ manuscriptId: manuscript.id, userId: manuscript.author_id })
}).catch(() => console.log('✅ Full analysis webhook triggered'))

// after
const { journey_id, timeout_at } = await startJourney(supabase, {
  journey_type: 'full_analysis',
  manuscript_id: manuscript.id,
  editor_name: 'alex',
  size_hint: { word_count: manuscript.current_word_count },
})
fetch(WEBHOOKS.alexFullAnalysis, {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ manuscriptId: manuscript.id, userId: manuscript.author_id, journey_id })
})   // no silent catch — errors bubble to an honest UI state
```

The `.catch(() => log)` pattern is removed everywhere. Errors either bubble to `try/catch` (with an honest failed-state UI) or trip `pollJourney`'s timeout path.

## 5 · Polling replacements

Each existing `pollForXxx` function becomes a thin wrapper around `pollJourney(journey_id)`. The domain-table reads inside them are removed; UI updates from journey row transitions.

| Existing function | Line | New behaviour |
|---|---|---|
| `pollForAnalysisCompletion` | L974 | Polls journey_id from call sites a/b/c/d; on `ready` triggers the same UI updates it does today (setAnalysisComplete, load summary/key_points from manuscripts — one-off read at ready, not a poll) |
| `pollForSamReading` | L1512 | Polls journey_id from call site e/f |
| `pollForChapterIssues` | L2415 | Polls journey_id from call site g; on `ready` loads issues from `manuscript_issues` once |
| Inline poll in `handleFreshAnalysis` | L659 | Same as pollForAnalysisCompletion |

**Content still lives in domain tables** (`manuscripts.manuscript_summary`, `manuscript_issues`, etc.). Journey rows are the state; domain rows are the content. Once a journey reaches `ready`, we do ONE read of the domain table for the content and stop polling. This preserves the "polls stay pure reads" law (§P5) — pollJourney only reads the journey row, and the terminal-state content read is a one-off, not a poll.

## 6 · n8n side (needs Paul's deployment)

For each workflow to satisfy E2 and E3, it must — from its start node and its terminal branches — write status transitions back to `as_journeys` using the service-role credential. The dispatch spec says this explicitly:

- On entry: `UPDATE as_journeys SET status='received', received_at=now() WHERE id=<journey_id from payload>`
- On terminal success: `UPDATE ... SET status='ready' (or 'replied'/'complete' by journey_type), completed_at=now()`
- On terminal failure: `UPDATE ... SET status='failed', terminal_reason=<short string>, completed_at=now()`

**Nine workflows to instrument** (matching the call sites above): `alex-full-manuscript-analysis`, `generate-summary-points`, `generate-chapter-summaries`, `sam-full-manuscript-analysis`, `jordan-full-manuscript-analysis`, `{alex,sam,jordan}-chapter-analysis` (three), `{alex,sam,jordan}-chat` (three), `generate-manuscript-version`. Total: eleven workflows if the three per-phase variants of chapter-analysis and chat are separate deployments (they are per the config).

**Backward compatibility:** any workflow that ships without the writeback wiring continues to run its business logic; the journey row stays `submitted` and the reaper closes it as `reaped` at `timeout_at`. The UI will show an honest failed-state message. This means we can ship the app-side changes without waiting for all eleven workflows to be updated — un-instrumented workflows just fail the E2 test (which is fine per-workflow, not fine at the E2 exit criterion overall).

**Sequencing suggestion (yours to call):** ship the four most-fired workflows first (`alex-chat`, `alex-chapter-analysis`, `alex-full-manuscript-analysis`, `generate-summary-points`) so the Alex flow proves the pattern end-to-end; then batch the Sam/Jordan variants; then `generate-manuscript-version` last.

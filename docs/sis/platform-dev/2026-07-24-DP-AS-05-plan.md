## 2 · Gate design

The gate is a first-class function that returns a `GateResult` — pass with the four machine-checked conditions verified, or reject with a structured reason. **The gate replaces both the `areAllChaptersApproved` soft check AND the ungated `handlePhaseTransition` path.**

### Location

New file: `src/lib/phase_gate.ts`. The existing `transitionToNextPhase` in `helpers.ts` is refactored to use the gate; the ungated inline flow in `phase-transition/page.tsx` is replaced with a call to the same gate.

### Signature

```ts
export interface GateReject {
  ok: false
  reason: 'unapproved_chapters' | 'missing_approval_actors' | 'snapshot_failed' | 'next_phase_activation_failed'
  // For 'unapproved_chapters': the concrete list. Named, not counted.
  unapproved?: Array<{ id: string; chapter_number: number; title: string }>
  // For 'missing_approval_actors': chapters approved post-epoch with no actor.
  anonymous?: Array<{ id: string; chapter_number: number; phase: number; approved_at: string }>
  // For other failure modes: a short deterministic message.
  detail?: string
}
export interface GatePass {
  ok: true
  approved_count: number
  snapshot_id: string
  next_phase_number: number
  next_phase_started_at: string
}
export type GateResult = GatePass | GateReject

export async function checkAndAdvancePhase(
  supabase: SupabaseClient,
  manuscript_id: string,
  from_phase: PhaseNumber,
  editor_name: EditorName,
  journey_id?: string,   // optional — passed if the caller already started J5
): Promise<GateResult>
```

### Sequence inside the gate

1. **Pre-check (a) approved count == chapter count.** Read chapters for the manuscript; separate approved vs unapproved by `phase_N_approved_at IS NOT NULL`. If any unapproved: return `GateReject` with the named list. Do NOT proceed.
2. **Pre-check (b) actor on every post-epoch approval.** Read chapters where `phase_N_approved_at >= '2026-07-24T00:00:00Z' AND phase_N_approved_by IS NULL`. If any: return `GateReject` with the anonymous list. (This should be zero given the DB trigger works, but the gate checks.)
3. **Advance (c) create snapshot.** Call `createApprovedSnapshot` from `helpers.ts`. If false: `GateReject` with `snapshot_failed`. Return the inserted `manuscript_versions.id`.
4. **Advance (d) mark current phase complete + activate next phase.** Do the two `editing_phases` updates and the `manuscripts.current_phase_number` update from the existing `transitionToNextPhase`. If any fail: `GateReject` with `next_phase_activation_failed`.
5. **Return `GatePass`** with the four verified values (count, snapshot_id, next phase number, started_at).
6. **Journey terminal write.** If `journey_id` was passed, the caller (not the gate) writes the J5 terminal (`complete` or `rejected` with reason). The gate returns the result; the caller decides how to surface it.

### Why not a DB function

Keeps the gate readable and testable in TypeScript. The four criteria are checked with normal Supabase queries; RLS is respected. If we later want harder guarantees (a DB constraint that `phase_N_approved_at` can only be set alongside `phase_N_approved_by`), that's SysAdmin territory — the app-side gate stays honest to what it can see.

## 3 · Reject surface UX

For `unapproved_chapters`, the reject surface renders on **the same page the user clicked "transition" from** — either the studio's completePhase flow or the phase-transition page. No silent bounce, no partial state.

Shape:

```
Transition cannot complete yet.

3 chapters still need your approval before this phase can end:
  • Chapter 4: "The first mistake"
  • Chapter 7: "Recurrence"
  • Chapter 12: "A second look"

[Open Chapter 4 →]  [Open Chapter 7 →]  [Open Chapter 12 →]
```

Each button routes to `/author-studio?manuscriptId=…&chapterId=…` so the user can jump directly to what's missing. Chapter numbers not counts — the RDP §3 rule.

For the rarer failure modes (`missing_approval_actors`, `snapshot_failed`, `next_phase_activation_failed`), the surface shows a concise "This didn't complete: <reason>" with a "Try again" button. Detail goes to the console + gets logged as the J5 `terminal_reason`. These are not expected in normal operation — they represent DB machinery having gone sideways, and the user's remedy is either retry or escalate.

### Where the surface lives

- **In `phase-transition/page.tsx`**: replace the current inline transition with a `checkAndAdvancePhase` call. On `GateReject`, render the reject panel above/instead of the celebration banner. On `GatePass`, keep the existing celebration + redirect.
- **In `author-studio/page.tsx` `completePhase`**: replace the current soft check with a `checkAndAdvancePhase` call. On `GateReject`, render an inline error panel in the studio's issues/notification area (small, non-modal) with the named list. On `GatePass`, keep the existing celebration chat message and the "Meet Sam"/"Meet Jordan" button.

## 4 · approveChapter defence-in-depth (E3)

Small edit to `src/lib/supabase/helpers.ts:137 approveChapter()`. Currently:

```ts
export async function approveChapter(supabase, chapterId, phaseNumber, content) {
  const phaseColumn = `phase_${phaseNumber}_approved_at`
  const { error } = await supabase
    .from('chapters')
    .update({ [phaseColumn]: new Date().toISOString(), content, updated_at: new Date().toISOString() })
    .eq('id', chapterId)
  ...
}
```

After DP-AS-05:

```ts
export async function approveChapter(supabase, chapterId, phaseNumber, content) {
  const { data: { user } } = await supabase.auth.getUser()
  const actorColumn = `phase_${phaseNumber}_approved_by`
  const timestampColumn = `phase_${phaseNumber}_approved_at`

  // Resolve the author_profiles.id for the current user — the trigger does
  // this too; we do it explicitly for defence-in-depth per E3.
  let approved_by: string | null = null
  if (user) {
    const { data: profile } = await supabase
      .from('author_profiles')
      .select('id')
      .eq('auth_user_id', user.id)
      .maybeSingle()
    approved_by = profile?.id ?? null
  }

  const { error } = await supabase
    .from('chapters')
    .update({
      [timestampColumn]: new Date().toISOString(),
      [actorColumn]: approved_by,   // explicit — trigger is now a safety net
      content,
      updated_at: new Date().toISOString(),
    })
    .eq('id', chapterId)
  ...
}
```

If `approved_by` resolves to null (unusual — the user is somehow unauthenticated), we still write the timestamp; the trigger's `IF NEW.phase_N_approved_by IS NULL THEN NEW.phase_N_approved_by := actor` covers the gap, and if the trigger also can't resolve, `inv_11` catches it.

## 5 · Journey J5 wiring changes

DP-AS-02 already creates a J5 journey (`phase_transition`) before the version-generation webhook fires (both from `phase-transition/page.tsx:114` and from the Phase 3 complete button in `author-studio/page.tsx:3303`). What DP-AS-05 adds:

- **On `GatePass`**: after the gate returns pass, the caller writes the J5 terminal directly (not via n8n): `UPDATE as_journeys SET status='complete', completed_at=now() WHERE id = journey_id`. This is a client write, but J5 doesn't have workflow writeback for the transition-itself work (only the version-generation sub-webhook does). The `complete` terminal here represents the gate's verdict, not the workflow's.
- **On `GateReject`**: the caller writes `UPDATE as_journeys SET status='rejected', terminal_reason=<reason>, completed_at=now() WHERE id = journey_id`.

**Wait — this is an app-side write on the poll path.** DP-AS-02's law was "polls stay pure reads." The transition action isn't a poll; it's a user action, and writing a terminal to as_journeys from the action's completion is legitimate — same shape as a service-role write, just from the user side. Confirmed against the RLS spec: authenticated users can INSERT their own journey rows (which they do via `startJourney`), but the RLS on UPDATE is worker/service-role only. **This means the terminal write from the app will fail RLS.**

Two options:
- **A · Extend RLS** to allow the creating user to write J5 terminals on their own rows. SysAdmin territory; small delta.
- **B · Move the J5 terminal write into a Supabase Edge Function** invoked by the app; service-role bypasses RLS. More machinery.
- **C · Move the whole gate into a Supabase RPC** (SECURITY DEFINER function) that authenticated users call; the function does the gate check + terminal write internally with service-role permissions. Cleanest; SysAdmin territory but a small addition.

I lean **C**. Flagged as §7 open question 1.

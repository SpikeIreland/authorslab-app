## DP-AS-02 · Journey wiring (app + n8n) — demo-hardening, do first

**Problem (F-013):** the studio fires a webhook then polls domain tables and
*infers* completion; a killed workflow = spinning UI, no record.

**Work:**
1. App: before every J1/J2/J3/J5 webhook call, INSERT an `as_journeys` row
   (scan on arrival) with `timeout_at` per RDP §2 (full analysis 20min
   size-scaled ×2 over 80k words; chapter 3min; chat 90s; transition 8min).
   Pass `journey_id` in the webhook payload.
2. n8n (coordinate with Paul for deployment): each Author Studio workflow
   writes back on entry (`status='received'`, `received_at`) and on terminal
   (`ready|replied|complete` + `completed_at`, or `failed` +
   `terminal_reason`) using the service-role credential. The `journey_id`
   travels in the payload — never through an LLM prompt (law 3).
3. App: replace completion-inference polling with a poll of the journey row
   (pure read). On `failed`/`reaped`, show an honest state — no infinite
   spinner.

**Exit criteria (all must demonstrate):**
- E1: every studio-initiated webhook call is preceded by a journey row
  (grep + runtime check: N calls ⇒ N rows).
- E2: kill-test — deactivate a workflow, fire the action: UI reaches an
  honest failed/reaped state within timeout+5min; `as_journeys` holds the
  corpse with reason; nothing spins forever.
- E3: happy path — J1 on a test manuscript: submitted→received→ready visible
  in the journey row; polls issue zero writes (verify via pg audit or code
  review of the poll path).

## DP-AS-04 · UCO minimum — acknowledgment + completion notices

**Pattern:** Clarence UCO C1 (proven). One truth: the existing `notifications`
table; in-app bell and any email are two lenses over the same row. No
AI-generated prose to users — deterministic templates only.

**Work:**
1. On J1 submit (full analysis): instant deterministic ack notification
   ("Alex has started reading — we'll let you know when the read is done").
   For manuscripts >80k words, the large-workpiece variant ("this is a big
   book — careful processing; we'll email when ready").
2. On J1 terminal: `ready` → completion notice; `failed`/`reaped` → honest
   notice ("hit a snag — it's been logged and we're on it"). State-driven,
   from the journey row transition.
3. Email lens optional for September (in-app first); if built, one send per
   notification row, never a second source of truth.

**Exit criteria:**
- E1: submit → ack row within 5s, visible in-app (no silent receipt).
- E2: every J1 terminal state produces exactly one notice row (ready, failed,
  and reaped each tested).
- E3: zero notification content generated by an LLM (code review).

## DP-AS-05 · Phase-exit gates, first-class (G-AS-P1..3)

**Problem:** `areAllChaptersApproved` is a soft code check — a conditional,
not a gate. No reject surface exists.

**Work:** promote to a first-class gate at phase transition: pass requires
(a) approved count == chapter count, (b) every approval post-2026-07-24
carries `approved_by`, (c) snapshot row created, (d) next phase activated
with `started_at`. Reject returns the **named list of unapproved chapters**
to the author on the transition surface — nothing advances, no silent
partial state. Log pass/reject as a J5 journey terminal (`complete` /
`rejected` + reason).

**Exit criteria:**
- E1: transition attempt with 1 unapproved chapter → rejected, named list
  shown, phase state unchanged (DB-verified).
- E2: pass path → all four criteria machine-checked (not implied), J5 row
  `complete`.
- E3: `approveChapter` helper also writes `approved_by` explicitly
  (defence-in-depth over the DB trigger).

## DP-AS-06 · Analysis gates + retry wave (G-AS-A/C) — post-demo acceptable

**Work:** after each full/chapter analysis persists, run the deterministic
gate (artifact fields non-null for the phase; issue rows well-formed;
per-chapter coverage count == chapter count). Fail → one automatic retry
wave; second fail → journey `failed` + UCO honest notice + needs-fix entry.
Implement gate checks n8n-side at the end of each workflow (cheap SQL), with
the verdict written to the journey row.

**Exit criteria:**
- E1: induced coverage gap (delete one chapter's artifacts in a test run) →
  retry fires; on second failure journey `failed` with reason
  `gate:coverage_mismatch`.
- E2: no analysis reaches `ready` except through the gate (code path review:
  the only writer of `ready` is the gate step).
